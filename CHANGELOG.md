### Added
- **Five more ways a script reached a shell through a pipe are closed, and two false denials the rule was making are not.** All seven were found by adversarial review of the rule above AFTER it shipped, and every one is measured through the real stdin entry point, with the deletion replaced by a touch so a marker file says whether the shell really ran it — under both bash 5.3.15 and /bin/bash 3.2.57, because one of them only executes under 3.2 and 3.2 is what five launchd plists on this machine actually run. **Newly refused:** a carrier option whose argument is a SEPARATE word (`curl … | bash -O extglob`, `+O`, `-o pipefail`, `+o`, `--rcfile f`, `--init-file f`, `sh -o nounset` — the argument was being read as the script FILE, which took the whole segment out of the rule); a redirect whose TARGET is the pipe itself (`bash < /dev/stdin`, `< /dev/fd/0`, `0< /dev/stdin`, `<> /dev/stdin`, and the `sudo`/`zsh`/`source` spellings — the same `/dev/stdin`, `/dev/fd/0`, `-` list the walk already applied to an OPERAND was simply never consulted at a redirect); a process substitution routed through a numbered fd (`bash /dev/fd/3 3< <(curl …)`, the operand written after the redirect, and `exec 3< <(curl …); bash /dev/fd/3`, which opens the fd in an earlier command — the fd map is therefore built over the whole command line); a command substitution in the `-c` argument of a PIPE-FED carrier (`curl … | bash -c "$(cat)"`, `-c "$(cat /dev/stdin)"`, `bash -s -c "$(cat)"` — the script text is visible and reads the pipe anyway); and a lone trailing backslash (`curl … | bash \`), which names no file and which bash 3.2 executes while 5.3 errors. **No longer refused, because refusing them was wrong:** a carrier with `-n` (`… | xargs -n1 bash -n`, `cat f | env bash -n`, `| timeout 5 bash -n`, `| nice bash -n`, `| sh -n`, `| zsh -n`) parses its input and stops — it is the syntax check this repository's own suites run over every shell file, and nothing it reads is executed; without `-n` those same commands are still refused. And a pipe target that only exists after expansion but RESOLVES: `$HOME`, `$PWD` and `$TMPDIR` are the three variables this gate already resolves for every rm operand, so `ps aux | "$HOME/bin/filter.sh"`, `ls | "$PWD/tool.sh"` and `ls | "$TMPDIR/tool"` are allowed, while `"$HOME/bin/bash"` — which resolves TO a shell — is still refused and `$TOOL`, `$PAGER` and `${PAGER:-less}` still are too. **A pipe target this gate could not resolve now gets its own refusal** (rule: `unresolvable pipe target`) instead of borrowing the one above: `git log --oneline | $PAGER` was being told that it "feeds a script into a shell" and pointed at `PIPED_SCRIPT_EXCEPTIONS`, which describes a command the user did not write and offers a URL allowlist that cannot help. The new message names the word it could not resolve and gives the two spellings that make it go away (a literal absolute path, or a file operand). **New cost, stated rather than discovered:** with a pipe feeding the segment, ANY unreadable command substitution in a `-c` string is now refused, so `echo hi | bash -c "…$(date)…"` stops here; the same command with no pipe is untouched. **Three exception-list guards had no row behind them** and are now pinned: the attached spellings of the option family (`-xhttp://…`, `-K/tmp/x.conf`, `-o/tmp/x`, `-k`), two operands with the EXEMPT URL first, and the exempt prefix embedded inside another URL — each of those three could be deleted with the whole suite staying green. Host and owner matching stays CASE-SENSITIVE, decided rather than overlooked, and both spellings are pinned. Still out of scope and now listed rather than implied (KNOWN-RESIDUALS.md R4-b): `bash < file`, `bash script.sh`, `bash -c "$(curl …)"` with no pipe, `… | xargs -0 bash -c`, `bash <&3`, `curl … > >(bash)`, `busybox sh` and other non-shell consumers. New residual R4-c: the option-argument walk covers the bash/sh spellings, so `curl … | fish -d 3` is still allowed.
- **A script that reaches a shell through a pipe or a process substitution, and that this gate cannot read, is now refused (rule: `unscannable piped script`) — with one exception list holding this project's own install route.** This is a posture change, decided by the user on 2026-09-03, and it is the first refusal in the hook that says 拒絕執行 / "Refused to run" rather than 拒絕刪除 / "Refused to remove": nothing about it names a protected directory, so anything that greps this repository's refusals for 刪除/remove will not see it. The gap it closes was measured that morning through the real stdin entry point with the deletion replaced by a touch, so a marker file proves the shell really ran each one: `echo "rm -rf /etc" | bash`, `printf %s "rm -rf /etc" | sh`, `echo rm -rf /etc | sudo bash`, `echo "rm -rf /etc" | bash -s`, `… | tee /dev/null | bash`, `echo "rm -rf /etc" | source /dev/stdin`, `bash <(echo "rm -rf /etc")` and `curl -sSL … | bash` were ALL allowed, while their byte-equivalent heredoc (`cat <<EOF | bash`) and here-string (`bash <<< "…"`) spellings were refused — the difference was never what the script did, only where it came from. **What still passes:** a LITERAL producer, whose text is read and judged by the ordinary rules, so `echo hi | bash` and `printf ok | sh` are untouched and `echo "rm -rf /etc" | bash` is refused for `/etc` by name; and a URL prefix on `PIPED_SCRIPT_EXCEPTIONS`, which today holds exactly one entry, `https://raw.githubusercontent.com/sieg-wang/better-rm/`, covering the four install routes in README.md and nothing else. **Everything else is refused, including a producer the parser cannot classify** — there is no fail-open branch. **The cost, stated rather than discovered:** every other project's one-line installer (`curl -fsSL … | sh`) now stops here, as do `cat script.sh | bash`, `echo "$cmd" | bash`, relay stages (`… | tee f | bash`, `… | sed … | bash`), `source <(kubectl completion bash)`, `( … ) | bash`, and any pipe into a command word that only exists after expansion (`… | $CMD`). The refusal names the rule and gives two ways through (save the script and read it, or spell it as `bash -c '<command>'`) plus the constant to extend, because a refusal with no way out is how a gate ends up switched off. **The exception list is not an identity check:** it matches URL text on the command line, so an exempted fetch may carry only options that cannot move the fetch — measured, `curl -k --connect-to raw.githubusercontent.com:443:127.0.0.1:18443 -sSL <a URL matching the prefix byte for byte>` served attacker-controlled bytes from a loopback TLS server, and `--resolve`, `--proxy`, `--unix-socket`, `-K` and `-o` do the same. Four fail-open shapes were found by adversarial review of the design and closed before it shipped, each with its own row: `<&`/`0<&0` is fd duplication and does NOT take stdin away from the pipe (`curl … | bash 0<&0` executes the piped script under both bash 5.3.15 and /bin/bash 3.2.57); an unresolvable carrier word gets the same answer its here-string twin already got; a command substitution inside the carrier's own here-string or heredoc body is unreadable (`bash <<< "$(curl -s URL)"`); and a compound producer (`( curl … ) | bash`) has no single producer to classify. Still deliberately out of scope, disclosed as R4-b in KNOWN-RESIDUALS.md: `bash < file`, `bash script.sh`, `bash -c "$(curl …)"`, `eval "$(curl …)"`, `… | xargs -I{} bash -c "{}"` and non-shell consumers — so `cat f | bash` is refused while the one-character-different `bash < f` is not, and what this buys is that the gate stops being blind to a common shape, not that an adversary cannot get a script past it.
- **`~/.ssh` and `~/.claude` are protected, on both guards.** Neither was, and one of them only looked protected: yesterday `rm -rf "$HOME/.ssh"` was refused because an unresolved variable folded to `/` — the refusal named a `/` nobody wrote — while the literal `rm -rf ~/.ssh` and `rm -rf /Users/<you>/.ssh` were ALLOWED at the same revision, and are allowed at the previous release. Resolving `$HOME` (see Fixed) removed the accident and left the real gap in plain sight, which is what this closes. Losing `~/.ssh` is not a rebuild but a re-enrolment of every host and forge that trusts the key; `~/.claude` holds this machine's agent configuration, its hooks and the session transcripts — and on the agent path the hook that would have refused the command is loaded from it. **The semantics are exactly `/etc`'s, restated here because a protection described more broadly than it behaves is worse than none:** the directory ITSELF is refused and its contents are not, so `rm -f ~/.ssh/known_hosts.old` and `rm -rf ~/.claude/projects/<session>` stay allowed — the second deliberately, since `~/.claude/projects` is a multi-gigabyte session lake that gets pruned. A pattern whose PARENT is protected selects that directory's whole contents, so `rm -rf ~/.ssh/*` and `rm -rf ~/.claude/*` are refused exactly as `rm -rf /etc/*` is, while `rm -rf ~/.claude/projects/*` is not. Matching is on whole path components, so `~/.claude-backup` and `~/.sshfoo` are untouched. Every spelling that reaches the check gets one answer — `~/.ssh`, `"$HOME/.ssh"`, `$HOME/.ssh`, `"${HOME}/.ssh"`, `/Users/<you>/.ssh`, `~/.ssh/` — as do `sudo rm -rf`, `find "$HOME/.ssh" -delete`, `echo ~/.ssh | xargs rm -rf`, `bash -c 'rm -rf ~/.ssh'` and an unquoted heredoc body. The hook keeps them as leaf names in `HOME_DIRS`, joined onto the same `home` the protected-path check already receives; better-rm spells them `"$HOME/.claude"` and `"$HOME/.ssh"` in `PROTECTED_DIRS`; the drift guard compares all three lists as one set, so an entry added on one guard and forgotten on the other goes red. **`~/Library` is deliberately NOT protected**: clearing `~/Library/Caches/<tool>` is routine work, this list protects a directory rather than its contents, so adding it would buy nothing for the ordinary command while refusing `rm -rf ~/Library/*` — and an over-refusal on a gate with no override is a live cost. Allow rows pin that decision: adding `~/Library` turns them red. Measured over 63 everyday commands, old guard against new, exactly the intended rows moved and nothing else. RESIDUAL, stated rather than left to be found: `cd ~ && rm -rf .ssh` is still allowed, because the verdict is made from the command text against the tool call's cwd — the same shape allows `cd / && rm -rf etc`, it is not specific to these two entries, and it is the very workaround the unresolved-variable refusal recommends.

- `--` is honoured as the option terminator, by both `rm` and `rm --restore`. What follows it is a pathname rather than an option, which is what makes a file whose name starts with a dash nameable at all: `rm -- -dash.txt` deletes it and `rm --restore -- -dash.txt` puts it back. Previously a bare `--` fell through to the combined-option parser and died with `invalid option -- '-'`, so such a file could not be deleted by any spelling. **The two sides take different numbers of pathnames**: deletion accepts any number after the terminator, `--restore` accepts exactly one and refuses anything further (see Changed). Without the terminator nothing changes: `rm -dash.txt` is still refused as an invalid option, exactly as `rm(1)` refuses it, and a dash-leading argument directly after `--restore` is still reported as a missing argument so a mistyped `rm --restore -f` cannot silently name a file to restore.
- `/Applications`, `/Library`, `/Network`, `/System`, `/Users`, `/cores` and `/private` are protected. The list was Linux-only, so on macOS the guard answered "not protected" for every one of them — measured by driving `is_protected` from the commit before the fix, all seven. **What that costs was overstated here and is corrected:** this entry used to say that `rm -rf /Applications` "moved every installed application into the trash and exited `0`", and that is not reproducible. Those directories are firmlinks — `/usr/share/firmlinks` lists `/Applications`, `/Users`, `/Library`, `/private`, `/cores` and `/Volumes` — so the directory entry being renamed lives in the sealed, read-only system volume root (`diskutil info /`: `Volume Read-Only: Yes`), and neither `/` nor `/System/Volumes/Data` is writable by the logged-in user. Measured in the equivalent shape, a target whose parent directory is not writable: better-rm prints `無法移除 / Failed to remove`, exits `1`, and leaves the item where it was. What an admin user can wipe without root is the **contents** of `/Applications`, and this entry does not stop that, because protection is exact-path, as it already was for the Linux entries: the directory itself is refused and its contents are not, so removing a single app bundle still works. `/private` covers `/private` only — macOS `/etc` and `/var` are symlinks to `/private/etc` and `/private/var`, and the physical spellings remain unprotected because the list is compared literally.
- The macOS firmlink spelling `/System/Volumes/Data/...` is recognised as the same object as the root spelling, by both guards. `/Users/you` and `/System/Volumes/Data/Users/you` are the same device and the same inode — measured with `stat -f '%d:%i'` — and so are `/Applications` and `/System/Volumes/Data/Applications`. A firmlink is not a symlink: `readlink -f` hands either spelling straight back, so nothing ever canonicalised one into the other and **the `$HOME` protection had this hole from the first day** — `/System/Volumes/Data`, `/System/Volumes/Data/Users`, `/System/Volumes/Data/Users/<you>` and `/System/Volumes/Data/Applications` were all ordinary deletion targets, so the whole home directory was removable under that spelling. The `/System/Volumes/Data/` prefix is now mapped back before the list is consulted, so `rm -rf /System/Volumes/Data/Users/you` is refused exactly as `rm -rf ~` is. The criterion is not existence: a `/System/Volumes/Data/Users/<name>` that has not been created yet is refused too. The mapped path still goes through the same exact-path comparison, so `/System/Volumes/Data/Users/you/project` stays removable, and the prefix must align on a whole component, so `/System/Volumes/DataDrive/...` is untouched. This is a spelling correspondence, not proof of identity — and **the example this entry used to give had it backwards**: `/System/Volumes/Data/usr` is not something the data volume lacks, it is a real directory holding the data-volume side of the `/usr/local`, `/usr/libexec/cups` and `/usr/share/snmp` firmlinks (`/usr/share/firmlinks`), and the same `stat -f '%d:%i'` that pairs the spellings above gives it a *different* inode from `/usr`. It is mapped onto `/usr` and refused with it anyway, so what the rule refuses there is an existing directory that is not `/usr`. That is the fail-closed direction and it costs little: `/System/Volumes/Data/usr/local`, which really is the same inode as `/usr/local`, maps to `/usr/local` and stays removable. Conversely, two spellings of one inode produced by a bind mount or a hard-linked directory are outside the rule.

- `/System/Volumes` and each `/System/Volumes/<volume>` mount root are protected, the way `/mnt` and `/Volumes` already were. That is where a modern Mac mounts its own APFS volumes — `Data`, `Preboot`, `VM`, `Update` — and neither guard had it in the mount-parent rule or in the list. Items below the first level are unaffected.
- `/Volumes` and each `/Volumes/<disk>` mount root are protected, the way `/mnt` and `/mnt/c` already were. `/Volumes/<disk>` is where every external disk, Time Machine target and network share is attached on macOS, so naming one took the whole disk's mount point rather than a directory. The protection stops at the mount root: `/Volumes/Backup/old.log` and anything else inside a mounted disk is still removable. Both mount parents now run through the same block, so the `/mnt` behaviour is unchanged — measured path by path, the only verdicts this changes are `/Volumes` and its first level.


### Fixed
- **A line continuation before a `#` turned the comment rule back off, and two of the three scanners lost it.** `git status \<newline># it's fine<newline>/bin/rm -rf /etc` was **ALLOWED**, as was the `~/.ssh` spelling, while the same command without the continuation is refused. Bash deletes a backslash-newline pair before it tokenises anything, so the `#` after it really is at the start of a word and really does open a comment — and the deletion on the line after it really runs, measured under `/bin/bash` 3.2.57 and 5.3.15 with the deletion replaced by a touch. This guard tracked "start of a word" with a flag that the pair silently cleared, so the `#` was read as ordinary text, the apostrophe in `it's` opened a quote that ran to the end of the input, and the deletion was swallowed into it — the quote-to-end-of-input bypass the comment rule closed, reopened by two characters, and `/bin/rm` sidesteps the alias so both layers missed it. **Two scanners had to learn it, not one**: `commandSubstitutions` loses word-start for a second reason (both of its escape branches `continue` past the bottom-of-loop update), so `echo \<newline># don't<newline>$(rm -rf /etc)` and the backtick spelling stayed ALLOWED with the tokenizer half fixed — each half is now killed by its own row. `readParenthesized` already restored the flag through its own bottom-of-loop update and is deliberately untouched, with a row pinning that it was already right. The fix also removes four **false denials** measured the same way: `true \<newline># ; rm -rf /etc`, `ls \<newline># x; rm -rf /etc` and the two substitution spellings are comments that bash never executes (no marker file under either bash) and were all being refused; they are allow rows now. The rows that must NOT become comments are pinned from the other three directions — a continuation inside a word (`ls x\<newline>#y ; rm …`), after a closed empty quote, and inside double quotes — all three measured executing.
- **A here-string handed to a shell carrier is that carrier's script, and it was not read as one.** `bash <<< "rm -rf /etc"` was **ALLOWED** while the byte-identical heredoc `bash <<EOF<newline>rm -rf /etc<newline>EOF` was refused. bash reads its stdin as the program, measured with a touch payload under 3.2.57, 5.3.15, `bash -s` and `sh`: the marker appeared every time. The operator reached the word stream as a redirection and nothing handed its operand back as code. Sixteen spellings were measured ALLOW and now deny — the six carriers, `-s`, the quoted and backslash-escaped bodies, the `~/.ssh` target, and the `sudo`/`env`/`nohup`/`timeout` wrappers — and **two consumer sites had to change, not one**: `source /dev/stdin <<< "rm -rf /etc"` and the `.` spelling never reach the carrier branch at all (their heredoc twins were already refused), so the carrier-present body route needed the same arm. Each half is killed by its own row: removing the carrier-branch arm leaves `timeout 5 bash <<<` allowed, removing the body-route arm leaves `source /dev/stdin <<<` allowed. Ordinary here-string use is unchanged (`grep foo <<<"$var"`, `echo x <<<y`, `bash <<< "ls -la"`), and `bash <<< "rm -rf ./build"` stays allowed because the body is judged as code, not as a path.
- **`rm -rf ./build <<< /etc` was refused, naming a path the command never touches.** The operand scan skips a redirection and its operand because that operand is a filename, and `<<<` was missing from that list, so the here-string's operand was collected as a deletion target. The refusal read as if the gate had understood the command, which is the worst shape a false denial can take. Adding the token would have opened a hole on its own — this loop also runs for an **unresolvable** command word, which may itself be a carrier — so `CMD=bash; $CMD <<< "rm -rf /etc"` and `$(which bash) <<< …` are refused through an explicit arm, and both are pinned as deny rows; without it they were measured flipping to ALLOW.
- **`--restore` could not find a pre-upgrade record for a name holding both a backslash and a shell metacharacter.** Widening the v2 escape set with `\s \a \g \d` left the cheap pre-filter knowing only two spellings, the raw name and the CURRENT encoding. A v2 record written between the escaping's introduction and that widening spells such a name a third way — backslash doubled, the `;` left raw — so both needles missed, the line was skipped, and `--restore` reported NOT FOUND with the trash copy still on disk and no `--list` to fall back on. Fail-closed, and still unrecoverable. A third needle in the pre-upgrade encoding is now compared as well; loosening this filter cannot restore the wrong file, because it is only a pre-rejection and every line it lets through is still parsed and compared in full. Measured for the `;`, `&` and `$` spellings, with a name carrying only a metacharacter and one carrying only a backslash as controls. The **legacy five-field layout is unaffected and now has the test that says so**: the escaping and the `v2` marker arrived in the same commit, so a five-field record is always raw bytes — which is what the "pinned for both layouts" sentence above was claiming without a test behind it.
- **Three code anchors could not fail, a metacharacter test could not tell "escaped" from "never logged", and no gate parsed 13 tracked files.** The anchors that keep `KNOWN-RESIDUALS.md` honest and the two that keep the installer probe off the argv path were fixed strings matched against the whole file, so a commented-out corpse satisfied them: measured, renaming `log_file_is_bound` throughout and leaving one commented copy of the old definition keeps all 136 tests green, and a true revert of the probe to the pre-ceiling `hookArgs=["-e",source];` shape — working on macOS, since the ceiling it reintroduces is Linux-only — passed the installer suite 280/0 with both of its anchors reporting ✓. All three now read the live code and match a spelling. The metacharacter-escaping loop sourced a record it never checked existed: with no log the record is 0 bytes and sourcing an empty file does nothing, so moving the log one directory down (`--restore` moves with it, so the neighbouring round-trip test stays green) left all four rows passing; two positive controls now require a non-empty record that names the payload. And the suite manifest names six suites, so the 13 tracked files under `test/residual-harness` and the 593-line release script were executed by nothing at all — an unterminated `if true; then` appended to one of them left `./run-test-suites.sh` reporting "All repository test suites passed". A parse-only sweep (`/bin/bash -n` over every tracked shell file plus `better-rm`, `node --check` over every tracked JS file) now runs in the contract suite, and it fails loudly rather than quietly if it ever finds nothing to check. `/bin/bash` deliberately, not `bash` from `PATH`: 3.2.57 is the interpreter half of these scripts really run under here.
- **Disclosed, not fixed: a shell carrier whose script arrives on a pipe or a process substitution is not scanned.** `echo "rm -rf /etc" | bash`, `bash <(echo "rm -rf /etc")` and six more spellings were measured ALLOW through the real entry point, with a touch payload proving bash runs them, while the byte-equivalent heredoc is refused and the here-string form now is too. It is not patched here because the narrow rule is unsound — it would catch the literal-`echo` subset, leave `cat f | bash`, `curl … | bash`, `bash < file` and every other emitter open while reading as "fixed", and newly refuse `echo "$cmd" | bash` — while the rule that is sound refuses this repository's own documented `curl … | install.sh | bash` route. That is a change of posture rather than a bug fix, so it is written down as **R4** in `KNOWN-RESIDUALS.md`, with the eight measured spellings, and left for a decision.
- **The deletion log followed a link that was already sitting at its path, and a filename could put executable shell into whatever it landed in.** `[ ! -f "$log_file" ]` and `>> "$log_file"` both follow, and nothing ever bound the path to an inode: with a symlink planted at the log path, measured through the default route with no environment variable set, the target grew from 14 to 840 bytes, and every later deletion appends to it as well. A whole record is shaped like a shell pipeline whose fields are its commands, `encode_log_field` escaped only `\`, `|`, LF and CR, and the trash copy keeps mode 755 with its absolute path sitting in field 4 — so aimed at a shell rc the record **executes**: `;`, `&`, `` ` `` and `$( )` were each measured running a command out of a filename when the poisoned file was sourced. The log path must now be a **regular, owned, single-link** file, and all four clauses are load-bearing: a hard link passes the first three (`[ -L ]` no, `[ -f ]` yes, `[ -O ]` yes) and only the link count sees the second name — measured leaking 8 to 834 bytes against a three-clause version of this same check. The v2 escape set is widened with `\s` for `;`, `\a` for `&`, `\g` for a backtick and `\d` for `$`. Records written before this keep decoding, because the old encoder already doubled every backslash so no old spelling collides with a new escape, and `--restore` still finds a raw `;` in a pre-upgrade record under either spelling — pinned for both the v2 and the legacy five-field layout. **Mode is deliberately NOT checked**: a 0644 log, restored from a backup or living on a FAT or cloud mount, would otherwise kill logging and `--restore` together and in silence, and it buys nothing once owner and link count pin the inode. A refused log never stops a deletion — the item still reaches the trash, the process still exits 0, and the warning names the path — which is the behaviour a full state directory already had. The link count is read GNU-first (`stat -c '%h'`, then `stat -f '%l'`), and that order is the safety property rather than a preference: GNU's `stat -f` prints FILESYSTEM status, dumps 230 characters to stdout and only then exits 1, so the reverse order would read that dump as a link count, and this repo's CI is ubuntu-only. A symlinked state DIRECTORY still works, because only the final component is tested. RESIDUAL, stated rather than left to be found: `>` and `<` are still written raw, so a record can be shaped into a redirection even though it can no longer be shaped into a command; the check is check-then-act on a path rather than a pinned descriptor, because `/dev/fd/N` reads mode 200 on macOS and `{fd}>>` does not exist in bash 3.2; and `--restore` still READS whatever log is at the path, which is unchanged and no weaker, since anyone who can plant a link there can write the real file too.
- **The refusal for an unresolvable target told the user how to walk past every protected entry.** The message added yesterday closed with `Workaround: cd into the directory and name the target relatively, e.g. cd <dir> && rm -rf <relative path>`, and that shape is not judged at all: the verdict is computed from command text against the cwd of the tool call, with no `cd` threaded through it. Measured by driving the live hook from a cwd that is not the home directory, `rm -rf ~/.ssh` is refused while `cd ~ && rm -rf .ssh` returns **no decision** — and a PreToolUse hook that returns no decision does not block the call, so real `/bin/rm` runs with no trash copy, no prompt and no undo. It is not specific to that entry either; `cd / && rm -rf etc` and `cd ~/repo && rm -rf .git` have the same shape. On the agent path nothing else catches it: the shell is non-interactive, so better-rm's alias never expands. The message now asks for a **literal absolute path**, which is judged by the ordinary rules, and names a script file for the case where the path only exists at run time. What this does NOT do is close the `cd` hole — that needs the gate to model a mutable cwd, a change with its own over-refusal surface — so it stays disclosed, now with suite rows pinning both halves of the measurement instead of a sentence that can drift. Also corrected in the same pass: the disclosure list said the `-exec` branch let "an rm reached through `xargs`" through, and it does not when there is a literal operand to see — measured, `find . -exec xargs rm -rf /etc \;` is REFUSED, as are the `-exec sudo xargs` and `-exec xargs -0` spellings. The real gap is one shape wide, `find . -exec xargs rm -rf \;`, whose operands would arrive on stdin and which names no path; it is now an allow row rather than a sentence.
- **A line continuation walked the target straight past the agent-path hook.** `rm -rf \<newline>/etc` was ALLOWED. Bash deletes a backslash-newline pair before it tokenises anything, so that command runs rm on `/etc`; the hook kept the newline inside the word and produced the target `\n/etc`, which is on no list and matches no rule. On the agent path this hook is the only guard — no alias over rm, no trash, no ledger, no undo — and it was bypassed by pressing Enter early, with no shell trick and nothing to quote. Measured with `bash -c` and `od -c` rather than reasoned about: `/et\<nl>c` and `"/et\<nl>c"` both arrive as `/etc`, `'/et\<nl>c'` keeps the backslash and the newline (single quotes make it literal), and `r\<nl>m` IS the word `rm` — run bare it answered with rm's own usage message. The same misreading refused ordinary work in the other direction, and that is how it was found: a continuation line was parsed as a fresh command, so a line beginning with `"$HOME"` became an unknowable executable, was assumed to be rm, and had its operands refused with `/` as the target.
- **A declared entry that is a symlink was refused under one spelling only.** `/etc`, `/var` and `/home` are symlinks on macOS, so neither guard folded their case: `/ETC`, `/eTc`, `/VAR`, `/vAr`, `/HOME` and `/hOmE` were all allowed while the lower-case spellings were refused. Every declared entry that is a real directory folded correctly the moment its guard consulted the filesystem; a symlink is exactly where consulting the filesystem stops, because an argument that IS a link is deliberately judged by the link's own path. Both guards now compare `lstat` device+inode against every declared entry, so the question is "is this argument that entry" rather than "is this string that string" — which stays correct on a case-sensitive volume, where `/ETC` really is a different object. The hook reads inodes as BigInt: an APFS inode is routinely past 2^53 (measured, `/etc` is `1152921500312571429`), and a Number-typed inode is rounded, which would make two distinct links compare equal. What this widens, exactly: a hard link to a declared symlink is refused too, since device+inode names an inode while rm unlinks a name. Reaching that shape takes `linkat(2)` with `AT_SYMLINK_FOLLOW` cleared, and it is an over-refusal in the safe direction.
- **`/private/etc` and `/private/var` are protected.** This entry previously stated that they "remain unprotected because the list is compared literally", and that was the hole: macOS `/etc` and `/var` are symlinks into `/private` (measured, `readlink -f`), so the protected spelling and the directory actually holding the data were different paths, and both guards allowed the second one. Removing the resolved path destroys exactly what listing `/etc` is for. Both names are now on both lists. Matching stays exact, so `/private/etc/some-config` and `/private/var/folders/...` are ordinary work, and `/private/tmp` is deliberately absent because scratch work lives there.
- **A heredoc body is data, and the hook was reading it as shell.** `git commit -F - <<'MSG'` was refused, twice, on ordinary prose whose line began with a backtick-wrapped identifier: tokenised as shell, that line's first word is a command substitution, so the executable is unknowable, the command is assumed to be rm, and an operand carrying an expansion fails closed as `/`. A Makefile being written to disk was refused the same way. `<<` and `<<-` are now tokenised as one redirection operator plus its delimiter operand — both skipped by the operand scans, as `>` and its filename already were — and the body is lifted out of the word stream. Exactly one consumer gets it back: a shell carrier, where `bash <<EOF` has no `-c` and the body IS the script, so every rm in it still runs and is still refused (including `sh`, `zsh`, `bash -s` and the tab-stripping `<<-` form). Command substitutions are still read from the whole text, which keeps an UNQUOTED delimiter honest — there the shell really does expand the body, so `cat <<EOF` with `$(rm -rf /boot)` inside is refused — while a QUOTED delimiter makes the body literal and its span is skipped. Quoting the delimiter is the shell's own switch for whether a body can execute anything.
- **rm reached through `xargs` or `find` was not modelled at all.** `echo /etc | xargs rm -rf` and `find /etc -delete` both reached rm with a protected path while the hook extracted no targets. xargs matters more than it looks: it executes the command itself, so `/bin/rm` is reached directly, past the shell alias that would have used the trash. xargs is now unwrapped like `nice` and `timeout` (its value-taking options skipped by name, so `-n 50` does not eat the command), and an rm whose operands are completed from stdin fails closed — the same answer `rm -rf "$DIR"` already got, because a pre-execution gate cannot read a pipe. `find` is judged by what it does: `-delete`, or an `-exec`/`-execdir`/`-ok`/`-okdir` whose command is rm, makes it a deleter and the paths it walks are judged as rm targets. A find that neither deletes nor execs rm is a reader, and nearly every find is a reader, so `find /etc -name x` and `find / -type f -print` stay allowed.
  - **Superseded in part:** "an `-exec`/`-execdir`/`-ok`/`-okdir` whose command is rm" was decided by comparing the single word after the operator, and every wrapper this hook already unwraps in command position puts a different word there — see Fixed.
- **The command `find` runs through `-exec` was judged by its wrapper, not by the command behind it.** `find /etc -exec rm -rf {} \;` was refused while `find /etc -exec sudo rm -rf {} \;` was ALLOWED, and it deletes `/etc` the same way; so were `find . -exec env SAFE=1 command rm -rf /etc \;`, `find /usr -exec nice rm -rf {} \;` and the `timeout` and `nohup` spellings, in all four operators. The wrapper list was not missing — `sudo`, `env`, `command`, `nice`, `timeout`, `nohup` and the rest are all unwrapped when the same rm is written directly, which is why `sudo rm -rf /etc` was already refused — it was unreachable, living inline in the main scan loop while the find branch matched a bare word. It is now one function both callers ask, rather than a second copy of the list beside `find` waiting to drift. The `-exec` operand scan starts after the *unwrapped* command word, so a wrapper's own option operand (`sudo -u root`) is no longer read as an rm target. A wrapper in front of a non-rm command is still a reader (`find . -exec sudo ls {} \;`), and a wrapper in front of an rm with ordinary operands is still ordinary (`find . -exec sudo rm -rf {} +` inside a project). RESIDUAL, enumerated rather than left to be found: the two callers now share the wrapper LIST, not the DECISION, and behind `-exec` the branch still lacks command position's other three rules, so a shell carrier (`-exec sh -c 'rm -rf /etc' \;`, and the `bash`/`zsh`/`sudo sh` spellings), an rm reached through `xargs`, an unresolvable command word (`-exec $CMD -rf /etc`, `"$CMD"`, backticks) and a nested `find … -exec find … -exec rm` are all still allowed. Every one of them is allowed at the previous release too; none is new.
- **A variable anywhere in an rm target refused the command, and then blamed a `/` the user never wrote.** `rm -f "$LOGFILE"`, `rm -rf "$BUILD_DIR"`, `rm -rf "$HOME/projects/foo/build"`, `rm -rf "$PWD/dist"`, `rm -rf "$TMPDIR/mything"` — all denied, 10 of 10 ordinary variable-bearing commands measured, while the literal spellings were allowed. The mechanism was deliberate (an expansion folds to `/` so the gate fails closed) but the blast radius was not: `$(which X) "$ARG"` is an everyday shape. `$HOME`, `$PWD` and `$TMPDIR` are now substituted and the result goes through the **ordinary** protected-path check, so the variable spelling gets the same answer as the path it expands to: `rm -rf "$HOME"` still refuses, `rm -rf "$HOME/projects/foo/build"` does not. That allowlist is the whole of it — every other name, `$1`, `$@`, `$$`, `$( … )`, backticks and `${VAR:-default}` stay unknown and are still refused — and matching is on the whole name, so `$HOMEBREW_PREFIX` is not `$HOME`. Resolution stops for any name the command itself could change first: an `NAME=` assignment anywhere in the text (the prefix form `HOME=/ rm -rf "$HOME/etc"` was already a test row and is what caught the first version of this), `unset`/`export`/`declare`/`typeset`, and for `$PWD` any `cd`/`pushd`/`popd`. An absent, empty or relative value resolves nothing, because substituting an empty HOME would turn `$HOME/build` into `/build`. **The refusal message no longer lies**: an operand the gate cannot work out is reported as unknown rather than as a protected directory, it names the operand, it says which variables are resolved, and it gives the `cd <dir> && rm -rf <relative>` way through. Residual, disclosed in README and AGENTS.md: the values come from the hook's environment, so a variable that means something different at execution time is judged on the hook's value. A value carrying WHITESPACE is not resolved at all: unquoted it is not one path, the shell splits it and rm gets several operands, so substituting it whole compares a string no argument will ever equal — measured with `TMPDIR='/tmp/x /etc'`, `rm -rf $TMPDIR` removes /etc while the joined word is an ordinary unprotected path. Resolution is applied to TARGETS only, never to a command word, so `eval ${HOME} /System` is still refused where the literal spelling is not; that is the safe direction and it is older than this change. Checked by diffing 120,000 generated commands against their textually substituted forms: no case where the variable spelling was weaker than the literal one, and no case where the literal spelling's own verdict moved.
- **The gate could be made to run past its own timeout by the NUMBER of targets, and a timed-out gate does not answer.** Per-target cost is bounded, but how many targets a command has is the command's own choice, and a target that is a symlink costs twenty-six `lstat` calls because that is when the declared-entry comparison runs. Measured against a `/etc` that really is removed: `rm -rf <60,000 relative symlink operands> /etc` took **6,215 ms at the previous revision** in 300 KB of command text, and a 30 MB spelling of the same shape never answered at all — both past the live 5,000 ms hook timeout, which produces NO decision and does not block the tool call. This is older than variable resolution: judging every operand is what this gate has always done and the number of operands was never bounded; resolution only made the variable spelling as expensive as the literal one always was (60,000 `"$PWD"/link` operands: 65 ms before, 4,386 ms after, both now bounded). Judging now stops after **2,000 ms** and refuses what it did not read, naming how many of how many targets it judged and suggesting the command be split. A TIME budget rather than a target COUNT because per-target cost spans two orders of magnitude: a 5,000-target cap was tried first and refused `find . -exec rm …x6000` — 6,001 targets, 118 ms, deletes nothing, and pinned as ordinary by the suite. RESIDUAL, stated rather than discovered later: the tokenizing pass that produces the targets runs before the first check, at roughly 40 ms per megabyte, so a command large enough to outrun the timeout on parsing alone is not stopped here. Measured after: the 30 MB shape answers in 3.7 s.
  - **Amended:** the budget's clock was read once every 64 targets, on the measurement that 64 of the most expensive target cost about 5 ms — which holds only while a target's cost is bounded by an ordinary local filesystem, and this gate does not choose the filesystem. Measured with HOME on a macOS autofs `/home` (one `lstat` under it costs 9.7 ms against 0.001 ms under `/Users`, because every lookup goes through automountd), one symlink target costs 28.8 ms, a 64-target block is 1,843 ms, and the 2,000 ms budget was overrun to 3,687 ms: 120,000 symlink operands answered in 3,921 ms against the live 5,000 ms timeout. The clock is now read on **every** target, so the budget can be overrun by one target rather than by 64; the same command answers in 2,435 ms. Reading it that often costs nothing measurable — 20,000 cheap targets took 286 ms with the mask and 281 ms without it, because even the cheapest target is three orders of magnitude more expensive than reading a clock. A symlink target now costs twenty-eight `lstat` calls rather than twenty-six, `~/.ssh` and `~/.claude` having joined the declared list.
- **Every `find` operator after an escaped `\;` was invisible to every rule in the hook.** `find /etc -exec cat {} \; -delete` was ALLOWED, and measured in a sandbox real BSD find takes the tree from 4 files to 0. The `;` that closes an `-exec` clause has to be hidden from the shell, so it is written `\;` or `';'` — and the tokenizer turned all three spellings into the same one-character word with nothing beside it, so the find scan could not tell find's clause terminator from a shell command separator. It assumed separator and stopped, which ended the read at the first clause: `-delete`, a second `-exec rm -rf /etc \;`, `-name`, `-o`, all unread, against `/`, `~`, `.git` and `BETTER_RM_PROTECTED_DIRS` alike, and inside `bash -c` as well. No wrapper and no trick were needed, and `-exec … \; -delete` is the natural spelling of the shape. The tokenizer now records which words were written as unquoted shell operators, and the find scan asks. That flag is consulted for `;` and for nothing else: only `;` and `+` terminate a clause, so an escaped or quoted `|`, `&` or `(` still ends the read — measured, find itself answers `no terminating ";" or "+"`, exits 1 and removes nothing for those, so refusing them would be an over-refusal on a command that does not run. A bare `;` still ends the command, so `find . -exec ls {} ; -delete` is unchanged.
- **A padded `find` could run the hook past its own timeout, and a gate that times out is a gate that did not answer.** Two independent quadratics, both measured on the very command `rm -rf /etc` and both suppressing *every* rule in the file rather than only the find branch, because the padding prefix is inert and costs the attacker nothing. `'find . ' + '-exec sudo '*6000 + '; rm -rf /etc'` took **5,525 ms** against the hook's 5,000 ms `settings.json` timeout — the whole payload is 66 KB — and the same shape with `env` or `xargs` behaves the same; that one was introduced by the wrapper fix above, which re-scanned the entire word list from every `-exec`. `'find . ' + '-exec rm '*6000` took **210,178 ms**, and it takes the same 210 s at the previous release: the operand scan ran to end-of-words once per `-exec` whenever no `+` or `;` ever closed a clause. Each `-exec` clause is now consumed once, which is also what `find` itself does — the words after `-exec` are the command's own argv and `find` does not read a second `-exec` inside them. Measured after: 4 ms and 80 ms. The advance deliberately lands **on** the separator that ended a clause rather than past it; stepping over one would swallow the command behind it and `find . -exec sudo -u root ls {} \; rm -rf /etc` would stop being read as an rm at all, which is now a row of its own for `;`, `|`, `&` and a newline.
- **A glob was translated into a regular expression instead of matched against paths**, which was wrong in three ways at once. (1) `rm -rf /et[c]` was ALLOWED — measured with a fake rm printing its argv, bash hands it `/etc` — because nothing ever asked whether a pattern could name a protected directory; the same held for `/et?`, `/va[r]`, `/User[s]`, `/e*`, `/{etc,var}` and `/*`. (2) `rm -rf dist/*` was REFUSED, because `*` was turned into the regex `.*` and asked whether it matched `.git`; in bash a wildcard does not match a leading dot, so `dist/*` cannot select `dist/.git`. `build/*`, `node_modules/*`, `*.log` and a bare `*` were refused for the same non-reason and are now allowed, while `.gi*`, `.*`, `.g[i]t` and `{.git,dist}` — whose component starts with a literal dot — still are not. (3) The regex backtracked catastrophically: measured 0.93 ms at 20 stars and 8.8 ms at 34, roughly 1.35× per two more, so around 85 stars it passed the hook's 5,000 ms timeout, and a gate that times out is a gate that did not answer. The pattern is now brace-expanded and matched component by component with an iterative matcher that keeps one backtrack point per `*`, and wildcards never cross a `/`. `..` is collapsed lexically in patterns only — a pattern cannot be resolved at all, so without it `/Users/you/../*` is not recognised as `/Users/*`. RESIDUAL, stated rather than discovered later: with `shopt -s dotglob` a bare `*` does match dotfiles, and this guard cannot see a shell option; it models bash's default.
- Protected `/mnt` and its immediate mount roots by default to prevent deleting Windows drives from WSL ([#9](https://github.com/doggy8088/better-rm/issues/9)).
- Store deletion history outside `TRASH_DIR` to avoid macOS log write failures, while retaining legacy log fallback for restore operations ([#10](https://github.com/doggy8088/better-rm/issues/10)).
- Prevent trash-path collisions and late writers from overwriting an existing recovery entry; suffixed recovery paths remain compatible with `--restore`.
- `--restore` no longer deletes anything, by path or otherwise. The trashed item is staged in a directory this process creates exclusively and then put in place with a single same-filesystem `rename`, so an existing file or symlink is replaced atomically by the kernel. If an initially absent destination appears before publish, an unconfirmed restore aborts, returns the item to trash, and never makes that destination the target of even one `mv`.
- **An authorized restore could destroy a successor that appeared after the set-aside.** Consent to overwrite was latched into a `-f` publish policy and carried to the end of the call, but by then the object that consent named had already been moved into the trash and the destination was empty — so `-f` had nothing left to act on except something that arrived afterwards, which nobody consented to. Measured with an `mv` shim that plants a file at the destination the moment the set-aside frees it: `rm -f --restore victim.txt` exited `0` with that file atomically unlinked by the publish `rename`, absent from the trash and absent from any backup — the disappearance this tool exists to prevent, on the recovery path. The publish is now always `-n`, so the case fails closed: the restore returns `1`, the item goes back to the trash, the displaced old destination stays recoverable with `rm --restore <name>` and the message says so, and the successor is untouched. This is not the previously reported "force-restore destroys the destination's occupant", which was a different, static case already closed; consent still overwrites the occupant that was there when the restore began, and that occupant still goes to the trash first.
- `--restore` can now restore a trashed directory onto an existing file or symlink. `rename(dir, non-dir)` is `ENOTDIR`, and only a real-directory destination used to be cleared out of the way, so restoring a directory over a file, a symlink, or a symlink to a directory failed outright.
- A destination that `rename` cannot replace — a real directory, or any destination when the restored item is a real directory — is now cleared by **moving it into the trash** rather than by `rm -rf`. It keeps a deletion-log record under its own original path and is recoverable with `rm --restore <name>`, which the message states explicitly. An overwrite is a deletion, and deletions through this tool are recoverable. The residual race inside the trash-move can at worst move an unrelated directory into the trash, where it survives intact; it can no longer destroy one.
- `--restore` now works when the trash and the destination are on different filesystems (an external drive, a network mount, or a second APFS volume with the default `$HOME/.Trash`). A cross-device `mv` is copy-then-unlink, so the inode necessarily changes; requiring inode equality made every such restore fail *after* the trash source had been consumed, leaving the user's only copy in the staging directory while the log still pointed at a trash path that no longer existed. The acceptance test is now split by device, and a failed cross-device extraction prints the path where the data actually is.
- `--restore` exits `2` only when the item was restored but the staging directory could not be removed, and prints the leftover path. A partially successful restore never exits `0`. `1` continues to mean the restore did not happen, and its message names anything that could not be put back.
- Clearing the destination into the trash no longer half-copies onto a trash volume that cannot hold it. Across devices that move is a full copy: measured on a real 20 MB HFS+ trash volume with a 41 MB destination, it died of `ENOSPC` half way and left a permanent 20 MB half-copy nothing mentioned, the user's file stranded in the staging directory instead of restored, and the trash source already consumed. The landing filesystem is now measured first (`df` against `du`); when it does not fit — or when the trash move fails anyway while the destination is still, by inode, the object that was verified — the destination is set aside in place in an exclusively created `<name>.better-rm-displaced-XXXXXX` directory by a same-filesystem `rename`, which needs no space. The restore completes, both objects survive, and the message names the set-aside path and says `rm --restore` cannot reach it. Protected destinations (e.g. `.git`) never take that route.
- A destination that reached the trash but whose deletion-log record could not be written no longer tells the user to run `rm --restore <name>`, which would answer "no deletion record found". `move_to_trash` reports that state as its own exit code `3`; an ordinary `rm` still exits `0` there, exactly as before.
- `--restore` now says that `mktemp` is what is missing when it cannot create its staging directory, instead of only reporting that the directory could not be created. `--restore` hard-depends on `mktemp`; deletion does not.
- Detect protected removals nested inside shell carriers, `eval`, command substitutions, and chained `sudo`/`env`/`command` wrappers.
- The agent-path hook now judges what the argument NAMES, not only how it is spelled. It was purely lexical, so three whole classes of spelling reached a protected directory unrefused on the one path where it is the only guard, with no trash and no undo behind it. `rm -rf link/` — a trailing slash forces POSIX resolution of the final component, so it destroys the target's contents and leaves the link — read as an ordinary directory removal; so did `link/.`, `link//`, `link/./` and `link/..`, which lands on the parent of the *target*. On a case-insensitive volume (the macOS default) `rm -rf /USERS` was permitted while `rm -rf /Users` was refused, and `stat -f '%d:%i'` gives the two one device and one inode; the same held for every case spelling of every protected entry and of its `/System/Volumes/Data` firmlink form, and for the NFD spelling of a directory declared NFC in `BETTER_RM_PROTECTED_DIRS`. Case folding and Unicode normalisation are properties of the filesystem rather than of the string, and no list can enumerate them: `/Users` alone has 2^5 case spellings before Unicode. The hook now `lstat`s the spelling **as written** and takes the union of the lexical verdict and the resolved one, which is what `better-rm`'s own `is_protected` has always done. Three properties are deliberate. An argument that IS a symlink is still judged by the link's own path, because deleting a link cannot touch what it points at — `rm ~/applink` stays allowed, and the trailing slash separates the two cases by itself, since `lstat("link")` reports a link and `lstat("link/")` reports the directory. A path the filesystem cannot answer for — it does not exist, its parent is unreadable, a symlink cycle — keeps exactly the verdict it had before, so a home directory that has not been created yet is still protected. And the resolved path never *replaces* the lexical one: `/var/.` resolves to `/private/var`, which is not on the list, while the spelling as written is `/var`, which is. Measured cost: 5.3 µs per target, against the ~31 ms the hook already spends starting node.

### Changed
- `BETTER_RM_PROTECTED_DIRS` is honoured by `better-rm` itself, not only by the agent hook. The variable is the only interface for adding protection of your own, and the hook has always read it — while `better-rm` had no reference to it anywhere in the file, so a user who set it, watched their coding agent get refused, and concluded they were covered still had the directory removable by `rm`. Both guards now parse it identically: `:` separated, empty entries skipped, relative entries resolved against the working directory, and exact-match like the built-in list, so `secrets` is refused and `secrets/notes.txt` is not. Skipping empty entries is what keeps a trailing colon from resolving to `.` and making the working directory undeletable.
- Everything **inside** `.git` is protected, not just the `.git` directory itself. `.git` is now matched as a path COMPONENT by both guards, so `rm -rf .git/objects`, `rm -rf .git/refs` and `rm -f .git/index.lock` are refused. Previously the pattern list matched only a path that ENDED at `.git`, so the object store — as unrecoverable as the repository it is — was an ordinary deletion target: `rm -rf .git/objects` moved it to the trash and exited `0`. The agent-path hook already refused every one of those paths, so the two guards were answering the same path differently; better-rm is aligned onto the stricter side. **This denies one legitimate thing**: clearing a stale `.git/index.lock` by hand after an interrupted git operation. Use `/bin/rm -f .git/index.lock` for that — it bypasses this tool, so there is no trash copy. Whether a lockfile exemption should exist is a policy call the maintainer has not made. Names that merely contain `.git` are unaffected: `.gitignore`, `.github/workflows` and `vendor.git/objects` stay removable.
- The protected-path hook now treats a command word it cannot resolve before execution (`$CMD`, `$( … )`, or a backtick, in any quoting except single quotes) as if it were `rm`, because the shell only resolves it to a real command at run time. **This denies some legitimate commands.** Every verdict below was measured against the hook, not reasoned about.
  - The rule: for such a command, each operand is checked as if it were a deletion target. Words starting with `-` are treated as options and skipped. It is denied when any remaining operand is either dynamic (any expansion is folded to the worst case, `/`) or a statically protected path. A backtick region containing whitespace is a special case — it splits into separate words, so the fragment carrying the closing backtick is itself a dynamic operand and the command is denied *regardless of its operands*, including when it has none.
  - Now denied (previously allowed): `$(which docker) run -v $(pwd):/work img ls` · `"$(which docker)" run -v $(pwd):/work img ls` · `$(brew --prefix)/bin/rg "$PATTERN" src/` · `$(which git) -C $(pwd) status` · `$(which cat) $HOME/.zshrc` · `$(which echo) $USER` · `$(which echo) /etc` · `` `which git` status `` · `` `command -v ls` ``.
  - Still allowed: any static executable (`docker run -v $(pwd):/work img ls`), static operands (`$(command -v python3) ./build.py`), an expansion *adjacent* to an option (`$(which make) -j$(nproc) all`, `$(which git) -C$(pwd) status` — separating them with a space denies), single-quoted text (`$(which cat) '$HOME/.zshrc'`), `~/…` paths (`$(which cat) ~/.zshrc`; a bare `~` is denied because it IS the protected home directory), a backtick with no whitespace inside (`` `pwd` status ``), and `$( … )` anywhere other than the executable position (`cd $(git rev-parse --show-toplevel)`).
  - Frequency: not rare. `$(which X) "$ARG"` is an ordinary shape, and the reviewer of this change hit the denial twice while reviewing it. Expect it in normal sessions rather than once in a while; it is fail-closed, loud, and names the path it refused.
  - Workaround: write the command name directly (`docker run …`), or keep dynamic values adjacent to their option (`-j$(nproc)`), or single-quote them.
- `deletion.log` records now carry a `v2` marker and escape `\\`, `|`, newline, and CR in both path fields, so filenames containing `|` or a newline can be logged and restored. Records written before this change (no `v2` marker) are still read by `--restore`.
- Added `BETTER_RM_STATE_DIR` and XDG state-directory support for `deletion.log`.
- Restricted newly created state directories and deletion logs to user-only access.
- `install-hooks.sh -a opencode` can no longer write outside the project. It only checked whether the final destination was a symlink, so a symlinked ancestor such as `.opencode/plugins` or `hooks` left the final component non-existent, the check passed, and `mkdir -p` plus `cp` then created the plugin and the runtime hook outside the Git root — exiting 0 while doing it. Both destinations are now resolved to their physical path and required to land inside the physical Git root, and either one failing rejects the install before *either* file is written.
- The same containment now applies to every other agent, not just OpenCode. `install-hooks.sh` builds the settings path for the eight JSON-style agents (`claude`, `codex`, `cursor`, `copilot`, `antigravity`, `qoder`, `pi`, `grok`) by concatenating the *lexical* Git toplevel with a fixed subpath, and the settings merge inspects only the final leaf — which does not exist yet when the ancestor is the symlink. A symlinked `.claude`, `.codex`, `.cursor`, … therefore let `mkdir -p`, `cp` and the final `rename` all traverse the link: measured in an isolated repo, `-a claude` wrote both the runtime hook and `settings.json` outside the project root and exited 0 while claiming to be project-scoped. The settings file and the shared hook beside it are now both resolved to their physical path and required to land inside the physical Git root, before any directory is created or any file is copied, backed up or renamed. This applies to project-scoped installs only; a `--global` destination legitimately lives outside every repository and is unaffected.
- `rm --restore -- <file>` now refuses any further argument instead of interpreting it, and exits `1` without touching anything. `--restore` puts back exactly one item, so a second word after the terminator was previously either discarded in silence (`rm --restore -- a b` ignored `b`) or parsed as a flag — measured, `rm --restore -- victim.txt -f` exited `0`, force-replaced the destination with no prompt, and left zero trash entries, so whatever had been in the way was gone with no recovery path. **This breaks spellings that used to work.** `rm --restore -- <file> -v` no longer runs; write `rm -v --restore -- <file>` instead, and `rm -f --restore -- <file>` for a forced overwrite. Flags written before `--restore` are unaffected, and `rm --restore <file> -f` without the terminator is unchanged.
- `rm --restore` now exits `2`, not `0`, when the old destination had to take the in-place `<name>.better-rm-displaced-XXXXXX` route, and prints the set-aside path on **stdout as well as stderr**. **This changes an exit code that used to be `0`.** That route keeps the data — it never loses the occupant and it is not going away — but it is a degraded outcome: the displaced object sits outside the trash and outside the deletion log, `rm --restore` cannot reach it, and clearing it up is the user's job. Measured before this change: exit `0`, zero bytes of stdout, and the only trace of it on stderr, so `rm -f --restore x 2>/dev/null` was indistinguishable from a restore that left nothing behind. It is no longer a rare corner either — the route is reachable for files, symlinks, hardlinks and FIFOs rather than directories alone, and from an ordinary permission failure rather than only a full trash volume. `2` is the code this command already used for "restored, but a named residue is left behind"; the clean route still exits `0` and still prints nothing extra. The two stdout lines are uncoloured so a caller can read the path out of them.
- Whatever occupies a `--restore` destination now goes **into the trash** before it is overwritten, instead of being unlinked by the publish `rename`. Only the two shapes `rename(2)` cannot replace atomically — a real directory, or any destination when the restored item is a real directory — used to be cleared out of the way; every other occupant was destroyed. Measured before this change, with a file at the destination: `rm -f --restore -- victim.txt` exited `0`, printed nothing, took the trash from one entry to zero, and left the occupant in neither the trash nor the working directory — this is the "gone with no recovery path" half of the entry above, for the spelling that was never refused. The occupant now gets its own deletion-log record under its own original path and comes back with `rm --restore <name>`, which the message states outright. A symlink occupant is trashed as the link itself and is never followed. The interactive prompt keeps its shape: `y` trashes the occupant exactly as `-f` does, `n` still touches nothing at all. Ordering carries the guarantee — the set-aside completes before the publish, so a set-aside that cannot complete returns the staged item to the trash and exits `1` with the destination never touched. The existing fallbacks are unchanged and now apply to every occupant: a trash volume that cannot hold it, or a trash move that fails while the destination is still by inode the object that was verified, still take the in-place `<name>.better-rm-displaced-XXXXXX` route with the path named in the message; a protected occupant such as `.git` takes neither route, so the restore aborts and leaves the destination exactly as it was.
